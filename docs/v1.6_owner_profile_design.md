# PAID v1.6 — Owner Profile as Source of Truth

**Status:** Backlog (designed 2026-05-14)
**Triggered by:** v1.5.4 complete → next push is reducing onboarding friction

## TL;DR

Today, owner personalization is scattered across **5+ files**: `owner.json`,
`persona.md`, `sop.md`, `settings.json`, `counterparties/*/profile.json`,
plus env vars. Each file has its own schema, edit path, and update
cadence. Onboarding a new pilot means 8+ manual steps.

v1.6 introduces a **single canonical Owner Profile** that:
- Captures all owner personalization in one structured record
- Renders ("derives") the scattered files as views of the profile
- Is built up from 3 input channels: **document + conversation + links**
- Updates itself over time from usage observations
- Can be modified via interactive `/paid-setup` flows after initial onboard

The scattered files don't go away — they become **generated artifacts**.
Hand-editing them still works (escape hatch), but the profile is the
default source of truth.

## Owner Profile schema (proposed)

`~/.hermes/paid/owner_profile.json` (single canonical record):

```jsonc
{

  "owner_id": "jimmy",
  "name": "Jimmy Yin",
  "preferred_language": "zh",         // zh / en / ko / auto (per-cp detect)

  // Identity surface (was: owner.json identities[])
  "identities": [
    {"platform": "feishu", "user_id": "ou_...", "enabled": true},
    {"platform": "telegram", "user_id": "...", "enabled": true}
  ],

  // Voice / persona (was: persona.md)
  "voice": {
    "tone": "direct-friendly",            // preset or freeform
    "style_notes": "短句，少用感叹号，工程师风格",
    "self_description": "Founder...",

    "always_decline": [],

      "kind": "web",

    }

    "last_updated_at": "..."
  },

  // Sync metadata

  "updated_at": "...",

```

## Input channels — how the profile gets populated

### Channel 1 — Interactive `/paid-setup` (minimal-required wizard)

First-time setup: owner DMs bot with `/paid-setup`. Bot walks owner
through **3-5 must-haves** only:

```
PAID: 嗨！我帮你做个 5 分钟 setup。
1. 你叫什么名字？（cp 看到的称呼）
   → owner: Jimmy
2. 默认 escalate 哪些话题给你？发自然语言或选 [财务|招聘|客户|技术|other]
   → owner: 财务、客户、招聘
3. 你的语气偏好？[直接|友善|专业|简短]
   → owner: 直接 + 简短
4. 主要工作语言？[zh|en|ko|auto]
   → owner: zh
5. 每天能花多少 LLM cost？[$1|$5|$20|无限]
   → owner: $5

PAID: 搞定！我用 default founder 模板填了剩下的部分。
随时发 /paid-setup 查看 / 修改任何字段。
也可以发一份你的 Lark Doc 或个人 SOP 链接让我扩充 profile。
```

Bot 把答案写入 `owner_profile.json`，调用 `derive()` 生成
persona.md / sop.md / settings.json。

### Channel 2 — Owner Document（Lark Doc / file）

Owner 在 Lark 写一份**结构化或自由格式的 owner doc**（可以是 SOP、
"about me"、工作风格描述等），把链接 DM 给 bot：

```
owner: 这是我之前写的工作 SOP https://jimmyresearch.feishu.cn/docx/xxx
```

Bot：
1. v1.5 LarkDocBackend 拉 doc 内容
2. LLM extract structured fields（"identify voice tone, top escalated
   topics, do-not-say phrases, language preference"）
3. **Diff vs current profile** → 显示 "我从你的 doc 提取到这些更新"
4. Owner 确认 / 编辑 / 拒绝
5. 接受的 fields 写入 profile，doc URL 加入 `references[]`，定期 re-sync

### Channel 3 — Conversation snippets + Links

Owner 在跟 bot 普通聊天中带出有用 info：

```
owner: 顺便你以后回复 cp 时别说"按规定办理"
       → bot 自动记到 voice.do_not_say

owner: 我的 GitHub https://github.com/... 你拉一下 readme 当 context
       → bot 用 web_scrape backend 抓，加进 references

owner: 以后客户类问题别让 cp 等太久，2 小时内必须回
       → bot 解析 → observed.preferred_decision_window_hrs = 2
```

Bot 不是被动接受 —— 每个 captured update 都给 owner 确认提示：
"我打算加这条到你 profile：xxx。确认？"

### Channel 4 — Usage Observation Learner（v1.6.x, after MVP）

Background module 跑 cron（每天/每周）：
- 扫 `audit_log.jsonl` + `pending_approvals.jsonl`
- 统计 approval_rate / 拒绝模式 / 高频 escalate topic / 平均 reply 长度
- 把统计写进 `observed.*`
- 发现可能的 profile drift（比如 owner 一直 reject "salary" 类问题但
  topics.always_escalate 没包含），主动 DM owner："注意到 X 模式，
  要不要更新 profile？"

## `derive()` — profile → scattered files

新模块 `paid/profile_sync.py`：

```python
def derive_from_profile(profile: OwnerProfile) -> None:
    """Render owner_profile.json into the legacy file surface.

    Idempotent. Writes:
      - owner.json (identities + preferred_platform)
      - persona.md (templated from voice.* + style_notes)
      - sop.md (templated from topics.* + voice.do_not_say)
      - settings.json (from preferences.*)
      - env-var overrides logged to plugin_runtime.log

    Does NOT overwrite per-cp profiles (those are runtime state).
    """
```

调用时机：
1. `/paid-setup` 完成最后一题
2. Owner 接受 Lark Doc 提取的 update
3. Owner 通过 conversation 接受了某个 captured update
4. Usage learner 应用 auto-approved updates
5. 手动 `/paid-resync` 命令

## `/paid-setup` 命令（v1.6 入口）

| 调用方式 | 行为 |
|---|---|
| `/paid-setup` (首次) | 5 题 wizard → 初始化 profile → derive |
| `/paid-setup` (已存在) | 显示当前 profile summary + 编辑选项菜单 |
| `/paid-setup voice` | 直接跳到 voice 编辑 |
| `/paid-setup topics` | 直接跳到 topics 编辑 |
| `/paid-setup add-doc <url>` | 主动添加 reference doc，再 extract |
| `/paid-setup resync` | 强制 re-fetch references + re-derive |
| `/paid-setup export` | 导出 profile.json 让 owner 备份 / 改后 import |
| `/paid-setup import <attachment>` | 上传 profile.json 全量替换（confirm-y prompt） |

## Migration from current files

v1.5.x → v1.6 升级：
- 首次启动 v1.6 时，PAID 检测有没有 `owner_profile.json`
- 没有的话，运行 `bin/migrate_to_owner_profile.py`：
  - 读 owner.json / persona.md / sop.md / settings.json
  - 用 LLM 把 markdown 内容解析成 structured 字段（voice + topics）
  - 写 `owner_profile.json`
  - 原 files 保留（owner 仍可手编；下次 derive 会同步更新）

### v1.6.5 — Non-review media enrichment
Today non-review media (cp sends "看这张图" + image, no /review) goes
through hermes' `vision_analyze_tool` — default `google/gemini-3-flash-preview`
via OpenRouter (~$0.00005/img, basically free). **Output is a scene
SUMMARY, not verbatim text.** Loses dense-text content (chat logs,
terminals, code, reports). PAID-side path adds OCR for quality
(not cost):
- [ ] pre_gateway_dispatch: detect non-/review media → run ImageBackend
      (tesseract) / PdfBackend (pdftotext) → stash result keyed by session_id
- [ ] pre_llm_call: look up enrichment → prepend to user_message
- [ ] Skip if hermes already added "[Image: ...]" prefix (avoid dup)
- [ ] Feature flag in settings.json: `media.enrichment_mode = "tesseract" | "vision" | "both"`
- [ ] Empty OCR → fall back to hermes vision (no PAID prepend)

Best for owners whose cps regularly share dense-text screenshots
(chat logs, terminal, code, reports) — OCR catches verbatim text vs
vision's summary. Free; saves $0.01/img.

### v1.6.4 — Per-cp physical isolation

- [ ] Split `pending_approvals.jsonl` → `counterparties/<cp_id>/pending.jsonl`
- [ ] `owner_profile.counterparties[].voice_overrides` + `sop_overrides`
      (some cps need more formal tone; some get extra topic carveouts)

- [ ] Legacy single-file readable one release for grace; deprecate after

Hygiene win — if owner `cat`s one cp's audit during debug, no other
cp's data leaks visually. Defaults stay sensible; most owners won't
need overrides.

## 设计选择 / Trade-offs

1. **JSON not YAML** —— PAID 已经在用 JSON storage（owner.json / settings.json），不引新依赖
2. **Profile 不存敏感凭据** —— FEISHU_APP_SECRET 等仍走 `.env`（不进 profile，避免误 export）
3. **derive() is idempotent + non-destructive** —— 不删 hand-edited 内容（merge 策略：profile 字段优先，但保留 file 里 profile 没覆盖的自由文本块）
4. **Owner 仍可手编** —— persona.md / sop.md 留着，profile 是 default source 但不强制
5. **i18n 个性化** —— v1.5.3 templates 写死，v1.6 后允许 profile 覆盖（per-key i18n override）

## post-v1.6 backlog（已记录，不在 v1.6 范围）

### Lark Doc edit capability (MERGE stage)

`paid_review/api.py` 的 MERGE 阶段当前 `raise NotImplementedError`。`SessionState.doc_edit_permission: Literal["none", "suggest", "direct"]` 字段已存在；lark-oapi 1.5.5 已装所有需要的 API（`docx.batch_update / patch / document_block_children.create` + `drive.file_comment / file_comment_reply`）—— **零新依赖**。

故意推后 v1.6 之后做的理由：
- bot 直接修改 owner 的 Lark Doc 是 **high-stakes** 操作
- 需要先把 owner profile 基础设施落地（v1.6.0），让 perm 是 owner profile 字段而不是 hand-edited config
- 每个 finding 的 edit 都需要 owner pre-approval，需要先有 v1.6.0 的 wizard / DM 卡片基础

落地时分三档：
1. `none` (default, 已 work as no-op)
2. `suggest` — `drive.v1.file_comment` 加评论 to accepted findings，owner 在 Lark UI 决定 (~3 天)
3. `direct` — `docx.v1.document_block.batch_update` 直接改 doc 内容 (~5 天 + snapshot + per-edit owner-confirm)

详见 task #44。

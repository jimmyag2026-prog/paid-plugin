# PAID v1.6.0 — Owner Profile as Source of Truth

**Released:** 2026-05-14 (continues from v1.5.6)
**Spec:** `docs/v1.6_owner_profile_design.md`
**Onboarding goal:** 30 min → 5 min

---

## What's new

v1.5.x scattered owner personalization across 5+ files (`owner.json`,
`persona.md`, `sop.md`, `settings.json`, `counterparties/*/profile.json`,
plus env vars). Each had its own schema, edit path, and update cadence.
Onboarding new pilots took 30 min of careful hand-editing.

v1.6.0 introduces a **single canonical Owner Profile**
(`~/.hermes/paid/owner_profile.json`) as source of truth. The scattered
files become **derived views**, auto-generated by `derive_from_profile()`.
Owner configures everything via 5-question DM wizard.

### Modules

- **`paid/profile.py`** — `OwnerProfile` dataclass with nested
  `Voice` / `Topics` / `Preferences` / `Observed` records. Tolerant
  load/save, default-fill on missing fields, type coercion on numeric
  strings, null-handling for malformed JSON.
- **`paid/profile_sync.py`** — `derive_from_profile(profile)` renders
  the canonical profile out to legacy files. Idempotent (twice → same
  output). Non-destructive merge: hand-edited prose outside managed
  markers (`<!-- paid:profile-managed:start/end -->`) is preserved.
  `settings.json` keeps unmanaged keys (l4c_enabled, retry policy, etc.).
- **`paid/setup_wizard.py`** — interactive `/paid-setup` state machine.
  First-time path = 5 questions (name, voice preset, escalate topics,
  preferred language, daily cost cap). Edit mode shows summary +
  per-field menu when profile already exists. TTL=15 min.
- **`bin/migrate_to_owner_profile.py`** — one-shot CLI to migrate
  existing v1.5.x pilots. Deterministic mapping for owner.json +
  settings.json; LLM-extracted voice + topics from persona.md / sop.md.
  `--dry-run` / `--force` / `--no-llm` flags.

### New slash commands

- **`/paid-setup`** — start wizard (first-time 5 questions or edit menu)
- **`/paid-setup cancel`** — cancel mid-wizard
- **`/paid-resync`** — regenerate derived files from current profile

### Architecture

```
owner_profile.json   ←  /paid-setup wizard + future doc-ingest + usage learner
       ↓ derive_from_profile()
       ├── owner.json     (identities + preferred_platform)
       ├── persona.md     (voice template)
       ├── sop.md         (topic policy)
       └── settings.json  (preferences)
```

Profile-managed sections in markdown files are marked with HTML comments
so hand-edited prose outside markers survives derive() calls.

Deferred to follow-up sprints (see `docs/v1.6_owner_profile_design.md`):

- **v1.6.1** — Doc/Link ingest (Lark Doc + web URL → LLM extract → profile)

- **v1.6.5** — Non-review media OCR enrichment (tesseract for dense text)
- **Post-v1.6** — Lark Doc edit (MERGE stage), 3 perm levels

## Sensitive credentials

`FEISHU_APP_SECRET`, `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY` etc.
**NEVER** flow through profile. They stay in `~/.hermes/.env`. Profile
is in principle shareable / committable to a repo.

---

## Backward compatibility

- No v1.5.x behavior changed. Existing pilots without `owner_profile.json`
  continue reading their scattered config as before.
- `derive_from_profile()` writes legacy files in the same v2 schema
  `paid.identity` already reads. Drop-in compatible.
- Hand-edited persona.md / sop.md prose survives `derive()` thanks to
  managed-section markers.
- Migration is **one-way** — running `bin/migrate_to_owner_profile.py`
  creates the canonical profile; from that point on, profile is the
  source. Hand-editing legacy files still works but will be overwritten
  next `derive()` (inside markers).

## Deploy

Same dep surface as v1.5.x — no new apt or pip deps.

After deploy, existing pilots optionally run:

```bash
sudo -u paid -H -- bash -c '
  cd ~paid/.hermes/plugins/paid-v1
  python -m bin.migrate_to_owner_profile --dry-run    # preview
  python -m bin.migrate_to_owner_profile              # commit
'
```

Or skip migration entirely and just use `/paid-setup` to build a
fresh profile from scratch.
